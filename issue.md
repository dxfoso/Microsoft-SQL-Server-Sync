Yeah, and I second language.# Incident and Local Architecture Regression Catalog

Last reviewed: 2026-08-15

This file records the failures observed while bringing the multi-client SQL sync system to its current design. It is a regression catalog, not a live operations log. Real client databases must remain out of automated verification; all architecture tests use fake local SQL Server clients.

## Current architecture and safety contract

Each Windows client captures only committed SQL Server Change Tracking operations after its durable cursor. Clients upload bounded chunks to the control plane. The server waits at the multi-writer upload barrier, combines operations from every participating client, chooses a durable latest-change winner, and exposes the merged result to every client. Each target applies the result through an atomic staging transaction and advances its cursor only after the complete participating batch succeeds.

The non-negotiable invariants are:

- A full snapshot, row-count difference, offline client, failed upload, comparison, or reconciliation may never imply deletion.
- Only an explicit Change Tracking `D` operation with a complete permanent primary key may delete a row.
- A unique/business-key collision may atomically replace only the older conflicting identity when deterministic latest-change metadata and the unique-key definition are available.
- An interrupted operation is all-or-nothing and safe to retry.
- An offline client does not block online peers; shared cursors wait until the offline participant catches up.
- Automatic scheduling, manual Sync All, recovery, and client updates are separate controls.
- At most one client per owner can be the conflict source. It wins only conflicting row/business-key identities; with no selection, the durable latest committed change wins.
- Every upload reads a fixed Change Tracking version-bounded database snapshot before network transmission; later database writes wait for the next sync job.

## Local verification

Run the normal architecture gate from the repository root:

```powershell
.\tests\run_sync_verification.ps1 -Profile Standard
```

It runs Flutter analysis/unit tests, repository contracts, updater path checks, a three-client SQL Server 2022 suite, atomic fault injection, concurrency, fuzzing, 5,000-row scale, SQL restart recovery, and a bounded soak.

Use the full SQL-version matrix when SQL syntax or version-sensitive behavior changes:

```powershell
.\tests\run_sync_verification.ps1 -Profile All
```

Fast focused checks are also available:

```powershell
flutter test
python tests/test_incident_regressions.py
.\tests\docker-sync\run.ps1 -Suite standard
```

## Coverage limits

Local Docker tests validate the synchronization architecture and SQL transaction semantics. They cannot perfectly simulate Windows UAC, every SQL Server installation permission model, native GPU/window behavior, physical power removal, or arbitrary WAN failure. Those boundaries require isolated Windows virtual machines or explicitly isolated fake live clients; they never justify testing against active production databases.
